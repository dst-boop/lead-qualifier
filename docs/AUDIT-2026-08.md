# State of the app — August 2026 audit

Requested: "analyze the current app, features, utility, results, code, and
UI/UX. Debug and clean it up. Make it more efficient. Remove unnecessary
components." This document is the analysis; the accompanying change is the
cleanup and the brand refresh.

## What the app is now

A lead-qualification workbench for wealth-management prospecting: four-stage
pipeline (Source → Enrich → Qualify → Track), multi-user with any-email
accounts, server-stored shareable lists, per-lead and list-scale enrichment,
a scoring model with a documented 80-point budget, money-in-motion signals,
and one-button outreach from any linked address.

**Load-bearing features, with their evidence base:**

| Feature | Grounding |
|---|---|
| Scoring + tiers (A/B/C/X) | 80-point budget, ADR §§2–17; excluded bucket keeps score |
| WhitePages enrichment | Verified against live responses; DOB → exact 59½ month |
| Free public records (FEC + SEC) | Both parsers confirmed against production; sweep at list scale |
| Money-in-motion signals | Age/tenure/WARN/8-K; coverage-honest since §26 |
| Senders & invites | Gmail aliases; calendar-only employer connections (§28) |
| Accounts | Any email; providers are attachments (§29) |
| Form 5500 / WARN | Schedule H/I join; prose-date parsing fixed against real NY data |

**Utility judgment:** the highest-value loop today is Source (sheet/CSV) →
sweep ⚖ (free) → 📞+ the A-tier (their birth month) → call order by score →
one-button invite. Everything in that loop is verified against live data.

## Debt found and paid in this change

- `/api/me` shipped a duplicated `zi_mcp_connected` key (harmless, wrong).
- Dead code: `_battle_key` (server), `ziConnected`, `fieldLabel`, a debug
  `__lastEnrich` global (client).
- The JSON backup/restore pair is a localStorage-era vestige; with server
  storage on, the server *is* the backup. Now hidden when `server_state`.
- The search box rebuilt the whole table on every keystroke — the one render
  cost a user feels constantly. Now debounced (160ms).
- Brass-era hardcoded colors (amber borders, old-navy hovers) bypassed the
  token system and would have survived any restyle. Folded into tokens.

## Debt found and deliberately not paid here

- **`main.py` is 4,400 lines and `index.html` 4,100.** Splitting them is
  real work with real regression risk, and the single-file frontend is a
  stated constraint (no build step). Revisit when a second developer joins.
- **The signals panel and the battles/team board** predate the account
  system; they work, but their per-user stats keying deserves a review pass
  now that identity is account-based. Not touched blind.
- **In-memory fallbacks** (`_MEM_SESSIONS`, `_MEM_ACCOUNTS`) are correct for
  dev and single-instance Cloud Run, but a second instance would split
  sessions. Firestore is the fix and is already the default in production.
- **wp-credits cache is per-process** — same shape, same answer.

## The brand refresh

The UI was re-skinned to the brand system (EA Blue / Warm White / Ice Blue,
Public Sans with extra-light headlines, accent blue for actions, mint used
twice). Mechanically: the palette lives in `:root` tokens the whole sheet
already consumed, so the refresh is a token swap plus one override layer —
no DOM changes, which is why every behavior test passed unchanged.

Two decisions worth recording:

- **Warm Gray (#988E85) fails AA contrast on Warm White** (≈3.3:1), and the
  brand lists accessibility as a principle above any single color. Secondary
  text therefore uses Dark Gray; Warm Gray is reserved for decoration.
- **Tier colors stay semantic** (green/amber/gray/red), re-tuned onto warm
  backgrounds rather than replaced by brand hues: A/B/C/X is a scanning
  language the brand palette does not speak, and "easy to scan" outranks
  palette purity in the same principles list.

The shield arcs appear once, quietly, in the header — one graphic focal
element per section, as specified.
